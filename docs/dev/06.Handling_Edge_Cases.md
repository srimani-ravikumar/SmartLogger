# A note on how I handled edge cases on my design approach

This section outlines how SmartLogger behaves under invalid inputs, misconfiguration, and runtime anomalies. The goal is to **fail fast, remain predictable, and avoid silent corruption of logs**.

---

## 1. Initialization & Lifecycle

**Logger access before initialization**

* `LoggerManager` throws `InvalidOperationException`.
* Rationale: Prevents undefined behavior due to missing configuration.

**Null configuration provider**

* `LoggerManager.Initialize()` and `LoggerFactory` enforce non-null contracts.
* Throws `ArgumentNullException`.
* Rationale: Logging cannot operate without a configuration source.

---

## 2. Input Validation

**Null type passed to `GetLogger(Type)`**

* Throws `ArgumentNullException`.
* Ensures API correctness and avoids ambiguous logger naming.

**Invalid or incomplete log message construction**

* `LogMessage.Builder.Build()` throws `InvalidOperationException` if:

  * Log level is missing
  * Message is empty
* Rationale: Guarantees every emitted log is meaningful and structured.

---

## 3. Configuration Handling

**Missing configuration file**

* `JsonConfigurationProvider.Load()` throws `FileNotFoundException`.
* Rationale: Fail fast instead of running with partial or default assumptions.

**Invalid configuration payload**

* Deserialization failures result in `InvalidOperationException`.
* Additional validation ensures:

  * Required fields are present
  * Appender definitions are valid

**Duplicate or unsupported appender destinations**

* Explicit validation rejects configuration.
* Rationale: Avoids undefined routing behavior and duplicate writes.

---

## 4. Logging Execution

**Log below threshold**

* `LoggerImplementation.Log()` exits early.
* Rationale: Avoid unnecessary processing and improve performance.

**Null or suppressed log message in appenders**

* `ConsoleAppender` and `FileAppender` safely ignore.
* Rationale: Defensive programming at output boundary.

---

## 5. File System & I/O

**Invalid or relative file paths**

* Paths are normalized using application base directory.
* Missing directories are created automatically.
* Rationale: Ensure logs are always writable without manual setup.

**Rolling on non-existent file**

* `SizeRollingStrategy` returns `false`.
* Rationale: Avoid unnecessary file operations.

---

## 6. Concurrency & Thread Safety

**Console output interleaving**

* `ConsoleAppender` uses minimal locking during write operations only.
* Ensures:

  * No mixed log lines
  * Maximum throughput

**Configuration reload storms (File watcher events)**

* Reload logic is:

  * Serialized via lock
  * Debounced with a short delay
* Rationale: Prevents duplicate reloads and inconsistent state.

---

## 7. Design Principles Applied

* **Fail Fast** → Invalid states are rejected immediately
* **Defensive Boundaries** → Appenders guard against invalid inputs
* **Thread Safety First** → Minimal locking, no shared mutable corruption
* **Operational Resilience** → System continues safely under partial failures
* **Predictable Behavior** → No silent fallbacks that hide issues

---

## To Sum up...

SmartLogger is designed so that:

> **Invalid configuration fails early, but runtime logging remains stable and non-blocking.**

This ensures reliability in both development and production environments without compromising observability.
