## System should support both synchronous and asynchronous logging modes

* By default, the framework should operate in **synchronous mode**. **Asynchronous mode** should be enabled only for high-throughput or performance-critical applications.
* **Synchronous mode:** Optimized for correctness.
* **Asynchronous mode:** Optimized for performance.

### Why this design works?

* Correctness first, performance next...
* Scale demands decoupling, but not every application requires it.
* SmartLogger keeps the default logging pipeline simple and predictable while providing an optional asynchronous execution model when higher throughput is required.

By default, the logging pipeline is **fully synchronous**, meaning:

* Every log message is processed on the **caller thread**
* Execution is **deterministic and predictable**
* Log ordering is **strictly preserved**
* Logging failures are **visible immediately**, rather than being hidden in background workers

This makes the framework **trustworthy by default**, which is critical for debugging, auditing, and production diagnostics.

### The reality: Scale demands decoupling

In high-throughput production systems, the workload is significantly different:

* Thousands of requests per second
* I/O-bound appenders
* Latency-sensitive operations

Under these conditions, synchronous logging can become a bottleneck.

Instead of redesigning the entire logging pipeline, SmartLogger introduces an **optional asynchronous execution layer**.

### The evolution: Optional asynchronous pipeline

For systems that require higher throughput, asynchronous logging can be enabled.

```text
Application Thread → Queue → Background Worker → Appender (I/O)
```

```text
Logger A ─┐
Logger B ─┼──► SAME AsyncWrapper ─► SAME FileAppender ─► File
Logger C ─┘
```

This model:

* Buffers log messages into a **bounded queue**
* Offloads I/O operations to a **dedicated background worker**
* Reduces request latency significantly
* Preserves the **same logging pipeline and appender implementation**

The asynchronous mode is implemented as a **Decorator Pattern** wrapper around the existing logging pipeline, allowing SmartLogger to scale without changing its core architecture.

### The trade-off: Performance vs. Reliability

Asynchronous logging improves application performance by moving the logging work to a background thread. However, this comes with a few trade-offs that developers should be aware of.

* **Queue overflow:** The asynchronous queue has a fixed capacity. If log messages are produced faster than they can be written, the queue may become full. Depending on the configured strategy, the framework can either block the caller thread or drop new log messages.

* **Possible log loss:** Log messages are temporarily stored in memory before they are written to the destination. If the application crashes unexpectedly, any messages still waiting in the queue will be lost.

* **Context preservation:** Since log processing happens on a background thread, execution context such as the correlation ID, timestamp, and thread information should be captured before the log message is added to the queue. This ensures the logged information accurately represents the original request.
